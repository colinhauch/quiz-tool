# Question Generation

> **[UNREVIEWED]** — The agent's editorializing needs a check, particularly the argument that exact numeric recall "is not knowledge worth having" and the claim that difficulty being composed (rather than stored) is what lets it escalate as a learner improves. Both read as the author's intent but are stated more strongly here than in the source.

Turning facts into things worth being asked. This concept sits between the graph and the learner: [../learning/](../learning/) decides *which fact* to ask about, and this decides *what the question looks like*.

## Question generators are pack-provided code

A question is produced by a **generator function the pack ships**, not by an engine-owned template filled from a data recipe. The engine hands the generator a statement (and a direction) and gets back a rendered question — prompt, input mode, options, distractors, difficulty. The engine knows how to *run* generators and *schedule* their output; it does not know how any particular kind of fact becomes a question.

Generators belong to the pack that defines the relation, because the relation is what determines what kind of question is even sensible. `borders` supports "which of these borders X" and select-all; `population` supports comparison and range questions but not exact recall. That is a property of the relation, and the pack that introduced the relation is the thing that knows it.

**Why code, not data.** An earlier draft made templates declarative data attached to relation types — additive and safe, but only able to express questions the engine's template runner anticipated. The moment a relation needs question logic that doesn't fit the recipe, data isn't enough. Since packs are first-party and already ship handler code (see [../packs/](../packs/)), letting them ship generators too removes the ceiling: any question a pack can write code for, it can ask. The engine never has to predict the shape of a future domain's questions.

The generation path: the scheduler picks a card, the card names a statement and a direction, the pack's generator for that relation produces the question (assembling distractors from the graph), and the engine displays it and logs the result.

## What's hidden is part of the question, not a detail

Knowing that Tokyo is in Japan and being able to produce "Tokyo" when asked for a city in Japan are **different skills**. They are tracked separately, and that decision propagates all the way into the card key — see [../learning/](../learning/). The two questions differ in *what the question hides*: the object in one, the subject in the other.

A question over one statement can hide the object, the subject, or a qualifier. Hiding the subject — "name a city in India" — is phrased through the relation's `inverse_of` declaration or through symmetric normalization, which is why those declarations exist on relation types at all: **the inverse edge is never stored.** "Name a city in India" is generated by phrasing `located_in` backwards, not by storing a `contains` edge. Storing both ways would double the graph and create a consistency problem for no benefit. A comparison hides a value from each of two statements, and so has no single hidden slot — see [../learning/](../learning/).

Qualifier questions (post-MVP) fall out of the same mechanism — a consequence of the answer log referencing statements rather than triples. See [../knowledge-graph/statements.md](../knowledge-graph/statements.md).

## Numeric facts don't get recalled, they get compared

We do not ask "what is Tokyo's population?" Exact recall of a large number is not knowledge worth having, and it is not knowledge anyone has. What people actually know is relative and approximate: Tokyo is bigger than Delhi; Tokyo is in the tens of millions.

So numeric relations get comparison, order-of-magnitude, and range-bucket questions instead. This is the reason the model refuses to make numbers entities — see [../knowledge-graph/](../knowledge-graph/) — and it is a product judgment expressed as an architectural constraint.

Comparison questions are the one place the model strains: a comparison is *about two statements*, but a card is keyed to one. The current approach synthesizes a virtual card keyed to the pair and logs both statement IDs, with one primary. This is the least settled part of the concept.

## Difficulty is composed, not stored

Difficulty comes from three dials rather than a field: which distractor strategy is used, how many options are offered, and which input mode is required. A hard question is siblings-as-distractors with text input; an easy one is far-away distractors with four choices. A pack's generator composes these dials when it builds a question; the engine supplies the learner's current level so the generator can pitch difficulty accordingly.

Composing it this way means difficulty can *escalate for the same fact* as the learner improves — multiple choice giving way to text recall as scheduler stability grows, without needing a second version of the fact.

Turning facts into things worth being asked. This concept sits between the graph and the learner: [../learning/](../learning/) decides *which fact* to ask about, and this decides *what the question looks like*.

## Templates are declarative recipes attached to relation types

A template is data, not code: a prompt string, an input mode, an option count, a distractor strategy, a difficulty, and a set of capability requirements.

They are attached to relation types rather than to entity types or packs, because the relation is what determines what kind of question is even sensible. `borders` supports "which of these borders X" and select-all; `population` supports comparison and range questions but not exact recall. That is a property of the relation, and putting templates anywhere else would mean re-deriving it.

Templates being data is what makes them **additive and safe**: a pack can add a template to an existing relation type without touching the engine, and without the redefinition problem that relation types have — see [../packs/](../packs/).

The generation path: the scheduler picks a card, the card names a statement and a direction, an eligible template is chosen (capabilities satisfied, difficulty appropriate), the prompt renders with localized labels, and options are assembled.

## Direction is part of the question, not a detail

Knowing that Tokyo is in Japan and being able to produce "Tokyo" when asked for a city in Japan are **different skills**. They are tracked separately, and that decision propagates all the way into the card key — see [../learning/](../learning/).

Three directions exist: forward hides the object, reverse hides the subject, and `qualifier:<name>` hides a qualifier. Reverse questions are phrased through the relation's `inverse_of` declaration or through symmetric normalization, which is why those declarations exist on relation types at all — **the inverse edge is never stored.** "Name a city in India" is generated by phrasing `located_in` backwards, not by storing a `contains` edge. Storing both directions would double the graph and create a consistency problem for no benefit.

Qualifier questions are free — a consequence of the answer log referencing statements rather than triples. See [../knowledge-graph/statements.md](../knowledge-graph/statements.md).

## Numeric facts don't get recalled, they get compared

We do not ask "what is Tokyo's population?" Exact recall of a large number is not knowledge worth having, and it is not knowledge anyone has. What people actually know is relative and approximate: Tokyo is bigger than Delhi; Tokyo is in the tens of millions.

So numeric relations get comparison, order-of-magnitude, and range-bucket questions instead. This is the reason the model refuses to make numbers entities — see [../knowledge-graph/](../knowledge-graph/) — and it is a product judgment expressed as an architectural constraint.

Comparison questions are the one place the model strains: a comparison is *about two statements*, but a card is keyed to one. The current approach synthesizes a virtual card keyed to the pair and logs both statement IDs, with one primary. This is the least settled part of the concept.

## Difficulty is composed, not stored

Difficulty comes from three dials rather than a field: which distractor strategy is used, how many options are offered, and which input mode is required. A hard question is siblings-as-distractors with text input; an easy one is far-away distractors with four choices.

Composing it this way means difficulty can *escalate for the same fact* as the learner improves — multiple choice giving way to text recall as scheduler stability grows, without needing a second version of the fact or the template.
